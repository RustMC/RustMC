# ADR-0008: M1 loopback development listener and lifecycle

Status: **Accepted for M1 infrastructure only** (29 September 2026).

## Context and constraints
M1 needs an observable bounded process while protocol, login, and world behavior remain absent. A bound socket cannot imply a playable server. The initial Linux development target and one-process architecture are already documented proposals; this record does not approve gameplay or protocol versions.

## Options considered
A general async runtime and protocol-shaped listener would add dependencies and premature semantics. A small standard-library TCP supervisor with signal handling keeps the M1 boundary explicit. A single loopback listener with nonblocking accept/read and bounded connection slots is sufficient for the local development gate.

## Decision
Use a loopback-only TCP development listener with one supervisor thread and no per-connection worker. A configured port of zero chooses an ephemeral port. The supervisor samples an atomic shutdown flag, emits key-value lifecycle events, and closes all sockets on stop. It never parses or replies with Minecraft packets. The only non-standard dependency added for M1 is a reviewed signal-handling library for SIGINT/SIGTERM; no custom signal handler or unsafe first-party Rust is needed.

## Consequences and risks
The polling interval adds bounded shutdown delay and is not an optimized event loop. Connection handling is intentionally minimal and unsuitable as a protocol gateway. The later Java and Bedrock gateways must replace or wrap this boundary only after their own versioned designs and tests. Log fields must not include raw configuration or client payloads.

## Tests and replacement criteria
Test pre-bind cancellation, bind conflicts, admission/byte/time limits, signal shutdown, socket cleanup, exit codes, and honest readiness events. Replace the supervisor when later protocol workloads demonstrate a need, while preserving observable lifecycle and bounded-admission contracts.
