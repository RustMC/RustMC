# ADR-0014: Policy for pursuing vanilla-compatible terrain generation

Status: **Accepted, amended 30 September 2026 to the knowledge-consultation
variant on explicit owner direction.** Originally accepted the same day as
the stricter black-box-only variant, decided from RustMC's existing
no-copying rules in AGENTS.md and the provenance policy.

On top of the five accepted items, one addition: the T0 oracle now also
extracts **publicly documented** structural facts of the 26.3 chunk storage
format (heightmaps relative to the world minimum Y, mixed blockstate palette
encodings, exact-width biome palettes) from the owner's own saves. Reading
how vanilla *stores* results is observation, not generation code
consultation, and feeds the protocol-output layer only.

## Context

The seed-2026 worksheet measured total divergence between RustMC's preview
generator and vanilla 26.3, and the
[feasibility spike](../research/vanilla-worldgen-feasibility.md)
inventoried the subsystems, data dependencies, and licensing questions a
parity effort would face. Since Java 26.1 Mojang ships deobfuscated jars,
which changes what "reference vanilla behavior" can practically mean. RustMC
must decide its evidence and copying policy **before** generator work starts,
not during.

## Decision

1. **Evidence hierarchy.** Compatibility facts come from official Mojang
   documentation and from measurements made against worlds generated by the
   owner's own licensed 26.3 client/server, read through the oracle tooling
   (region files, publicly documented format). Observed facts are recorded in
   `docs/research/` with method and date.
2. **Independent implementation, knowledge consultation.** RustMC writes its
   own generator in its own Rust. No code, data files, or architecture are
   copied or translated into the repository from Mojang binaries or from
   other server projects. Under the owner's explicit 30 September 2026
   direction, deobfuscated vanilla generation code and PaperMC's Java
   generation code **may be read for understanding** — to learn how the
   vanilla algorithm works — subject to three rules: (a) nothing consulted
   enters git, in any form (no files, no code fragments, no vendor
   references in tracked content); (b) RustMC's implementation is written
   independently from the understood behavior, not translated line by line;
   (c) every consultation is logged in `docs/PROVENANCE.md` with what was
   read, what was learned, and how the result was implemented. Numeric
   algorithm parameters learned this way are recorded as facts with that
   provenance before use.
3. **No Mojang assets or data in the repository.** Generated worlds, jar
   contents, and extracted constants never become committed files. Numeric
   values that can only be obtained from Mojang data require an explicit
   owner/legal sign-off entry in the provenance record before use.
4. **Staged gates, oracle first.** Work proceeds only through the T0→T4
   stages and match-rate gates defined in the feasibility spike; each stage
   lands with its own tests, timings, and documentation. Structures (T5)
   require a separate ADR.
5. **Preview remains the default.** The ADR-0013 synthetic preview generator
   stays in place, pinned by its worksheet regression test, until a vanilla
   stage passes its gate and the owner accepts the switch.

## Consequences

- The first implementation slice is tooling (T0 oracle), not world generation,
  so the decision can be revisited with data.
- Per-version validation becomes a standing cost; 26.3 parity claims must be
  restated for each game update.
- The original acceptance was black-box-only. The owner directed the
  knowledge-consultation amendment the same day, with the rule that nothing
  consulted may enter git; this ADR text is the signed record of that
  relaxation, and consultation sessions are logged in the provenance file.
  The EULA/legal-review item from the feasibility spike remains open and
  covers the residual question of shipping a seed-exact vanilla algorithm.
